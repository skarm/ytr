# Разработка ytr

Репозиторий содержит SDK, CLI, генератор и инструменты проверки контрактов Yandex Tracker. Пример интеграции находится в отдельном Go-модуле.

## Проверки

Запускайте команды из корня репозитория:

```sh
go test -race ./...
go vet ./...
go -C examples/integration test -race ./...
go -C examples/integration vet ./...
go run ./cmd/checkdocs
go generate ./...
git diff --exit-code -- methods_gen.go typed/models_gen.go typed/client_gen.go
```

Для дополнительной проверки используйте `golangci-lint run --config .golangci.yml ./...`.

Тесты работают с локальными HTTP-серверами и сохранёнными ответами, без запросов к Tracker и реальных учётных данных. Генерация и обычная проверка `checkdocs` не требуют сети. Тесты генератора проверяют компиляцию клиента и отклонение повреждённых схем; fuzz-тесты обрабатывают некорректные входы.

[CI](.github/workflows/check.yml) проверяет оба модуля, гонки данных, `go vet`, реестры и воспроизводимость генерации. Онлайн-сверка запускается вручную через `workflow_dispatch` с `online=true` и сохраняет отчёт как артефакт.

## Исходники и реестры

Контракты операций и моделей хранятся в следующих файлах:

- `api/catalog.json`: имена операций, HTTP-методы, пути и виды запросов и ответов
- `api/models.json`: типы, правила присутствия полей и привязки path/query/header/body/response
- `api/sources.json`: страницы источников, независимые HTTP-сигнатуры и решения по неоднозначным контрактам
- `api/documentation.json`: извлечённые таблицы параметров, отпечатки строк и опубликованные JSON-примеры
- `api/index.txt`: снимок индекса справочника
- `typed/testdata/requests.json` и `responses.json`: независимые ожидания запросов и ответов

Снимок `api/documentation.json` извлекается из официальных страниц, а не из схемы моделей. Ожидания в `typed/testdata` обновляйте по документации: генерация ожиданий из схемы скрывает общие ошибки.

`go generate ./...` воспроизводит `methods_gen.go`, `typed/models_gen.go` и `typed/client_gen.go`. Редактируйте реестры, затем запускайте генератор. Проверки из `internal/apidoc` используются и генератором, и `checkdocs`; ошибочные входные данные отклоняются до записи файлов. Для использования SDK генерация и чтение реестров не нужны.

## Обновление контрактов

Онлайн-проверка обращается к официальному справочнику и сохраняет отчёт в игнорируемый Git каталог `api-review/`:

```sh
go run ./cmd/checkdocs -online -report api-review
```

При изменениях команда возвращает ошибку и записывает `report.txt`, `report.json` и снимок кандидата. Отчёт показывает добавленные и удалённые страницы и поля, изменения типов и обязательности, строки источника и затронутые модели. Предложенные Go-типы не применяются автоматически.

Перед принятием обновления:

1. Сверьте изменения в отчёте с источниками.
2. Исправьте модели и привязки в `api/models.json`, при необходимости каталог и классификацию источников.
3. Обновите независимые ожидания в `typed/testdata` и вызывающий Go-код.
4. Примите проверенный кандидат:

```sh
go run ./cmd/checkdocs -accept api-review
```

`-accept` повторно получает страницы закреплённой revision и сверяет извлечённые факты. Затем в отдельном каталоге выполняет генерацию, тесты и `go vet` основного модуля, а также тесты примера интеграции. Только после успешных проверок команда устанавливает реестры, снимок источников и сгенерированные файлы.

Устаревший отчёт, неустранённые расхождения и параллельные изменения входных файлов блокируют принятие. При ошибке установки откат сохраняет обнаруженные правки пользователя. Для устаревшего отчёта запустите онлайн-проверку заново.

## Неоднозначные контракты

Если источник противоречит опубликованному примеру или не определяет форму значения, запишите обоснованное решение в `pages[].field_decisions` соответствующей страницы `api/sources.json`:

```json
{
  "section": "<after.section из report.json>",
  "digest": "<after.digest из report.json>",
  "model": "CreateIssueRequestBody",
  "field": "Unique",
  "type": "Optional[string]",
  "reason": "<обоснование со ссылкой на проверенный контекст>"
}
```

Решение привязано к строке, секции, модели, полю и текущему типу. Для строки без сопоставления поля `model`, `field` и `type` отсутствуют. Для удалённого поля используйте `before.section` и `before.digest`. Общее решение для страницы не разрешает расхождения отдельных полей.

Для страниц с несколькими операциями `operations[].sections` в `api/models.json` задаёт anchors разделов каждой операции. Общие разделы перечисляйте у всех использующих их операций. Исчезнувший anchor блокирует принятие.

Каждая HTTP-сигнатура снимка должна соответствовать операции SDK или иметь запись в `pages[].excluded_signatures`: `signature`, `digest` всей страницы и `reason`. При изменении страницы проверьте классификацию и обновите digest явно. Новые неклассифицированные сигнатуры и поля без владельца блокируют принятие.

После структурного редактирования моделей ориентируйтесь на имена типов и полей: JSON pointers в отчёте относятся к состоянию на момент его создания.
